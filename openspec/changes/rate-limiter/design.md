# Design

## Context

Пакет `src/rate_limiter/` содержит только docstring; тесты запускаются `python -m pytest` (check `tests-passed`).
Мотивация — proposal.md, раздел Why; поведение — `specs/rate-limiter/spec.md` (`REQ-RL-001`, `REQ-RL-002`).

## Goals / Non-Goals

**Goals:**
- Детерминированное поведение в тестах: время из внедрённого источника, без `sleep` и системных часов.
- Только стандартная библиотека Python 3.11+.

**Non-Goals:**
- Потокобезопасность, распределённое состояние, вытеснение ключей — см. Non-goals в proposal.md.

## Decisions

### D-1. Алгоритм — token bucket с ленивым пополнением

Каждому ключу соответствуют запас `tokens` (float) и отметка `last` (время последнего пересчёта). При запросе:
`elapsed = now - last`, `tokens = min(N, tokens + elapsed * N / W)`, `last = now`; если `tokens >= 1 - 1e-9` —
пропустить и `tokens = max(0, tokens - 1)`, иначе отклонить. Новый ключ создаётся с `tokens = N`, `last = now`.
Пересчёт выполняется и для отклонённого запроса: пополнение непрерывно, результат тот же. Скорость считается как
`elapsed * N / W`, а не `elapsed * (N / W)`: для целых значений времени это даёт точные границы `SCN-RL-002`
(1 с · 2 / 10 = 0.2, накопление 0.8 + 0.2 = 1.0). Допуск 1e-9 (`REQ-RL-002`) гасит ошибку округления float на дробном
времени (0.3 − 0.2 при N = 10, W = 1 даёт 0.9999999999999998).

Семантика квоты — token bucket (всплеск до N, скорость N/W), как задано в intent; строгое «не больше N в любом
скользящем окне W» не требуется (`REQ-RL-001`, находка F-1 первого review).

Отвергнуто:
- Fixed window (счётчик на окно): до 2N запросов на стыке окон при худшем среднем, нет непрерывного пополнения
  `REQ-RL-002`.
- Sliding log (метки всех запросов): даёт строгое «не больше N в окне», но память O(N) на ключ и не token bucket из intent.
- `fractions.Fraction` для запаса: точна на рациональных входах, но время источника — float, ошибка уже во входе.
- Фоновый таймер пополнения: требует потоков и реального времени, ломает детерминизм тестов.

### D-2. Внедряемый источник времени

Конструктор принимает `clock: Callable[[], float]` (секунды); по умолчанию `time.monotonic` — это «монотонные часы
процесса» из `REQ-RL-001`. Тесты передают фальшивые часы, продвигаемые вручную. Значение часов проверяется
`math.isfinite` (не `bool`, `int`/`float`) до изменения состояния; исключение часов не перехватывается.

Отвергнуто:
- `time.time()`: не монотонно, не управляется из тестов.
- Передача `now` в каждый вызов: переносит согласованность времени на вызывающего и расширяет API.

### D-3. API

`RateLimiter(limit: int, window: float, clock=time.monotonic)`; метод `allow(key: Hashable) -> bool`. Проверки
конструктора (`REQ-RL-001`, `SCN-RL-004`): `limit` — `int` и не `bool`, `> 0`; `window` — `int`/`float`, не `bool`,
`math.isfinite`, `> 0`; иначе `ValueError`. Состояние ключей — `dict` в памяти экземпляра: равенство ключей — равенство
ключей `dict`, нехешируемый ключ даёт `TypeError` при обращении к `dict` до любых изменений.

Отвергнуто:
- Исключение при отклонении вместо `bool`: отклонение — штатный исход, а не ошибка.

### D-4. Часы, идущие назад — не решено

Поведение при `now < last` зависит от `UNK-RL-001` и не реализуется до решения maintainer'а. Варианты для решения:
(а) считать `elapsed = 0` и сдвинуть `last` на `now`; (б) считать `elapsed = 0`, `last` не менять;
(в) `ValueError` из `allow`. Решение закроет UNKNOWN и добавит сценарий в spec.

> **UNKNOWN** `UNK-RL-001` · blocking — что делает ограничитель, если источник времени вернул значение меньше
> предыдущего (часы пошли назад)?

## Risks / Trade-offs

- [Память растёт с числом ключей] → вытеснение вне scope (proposal.md, Non-goals); отмечено в docstring.
- [Ошибка округления float] → допуск 1e-9 из `REQ-RL-002`; тест на дробном времени у границы.
- [Вызов из нескольких потоков] → вне контракта (`REQ-RL-001`); docstring предупреждает.
