# Design

## Context

Пакет `src/rate_limiter/` содержит только docstring; тесты запускаются `python -m pytest` (check `tests-passed`).
Мотивация — proposal.md, раздел Why; поведение — `specs/rate-limiter/spec.md` (`REQ-RL-001`, `REQ-RL-002`).

## Goals / Non-Goals

**Goals:**
- Детерминированное поведение в тестах: время из внедрённого источника, без `sleep` и системных часов.
- Только стандартная библиотека Python 3.11+.

**Non-Goals:**
- Потокобезопасность, распределённое состояние, вытеснение ключей — см. Non-goals в proposal.md.

## Decisions

### D-1. Алгоритм — token bucket с ленивым пополнением

Каждому ключу соответствуют запас `tokens` (float) и отметка `last` (значение часов при предыдущем запросе). При запросе:
`elapsed = max(0, now - last)`, `tokens = min(N, tokens + elapsed * N / W)`, `last = now`; если `tokens >= 1` —
пропустить и `tokens -= 1`, иначе отклонить. Новый ключ создаётся с `tokens = N`, `last = now`. Пересчёт выполняется и
для отклонённого запроса: пополнение непрерывно, результат тот же. Скорость считается как `elapsed * N / W`, а не
`elapsed * (N / W)`: границы `SCN-RL-002` точны в двоичной арифметике (N = 2, W = 8: 3 с · 2 / 8 = 0.75,
накопление 0.75 + 0.25 = 1.0). Сравнение с единицей точное, без допуска (решение maintainer'а по находке F-1 второго
review): на дробном времени решение на границе может определяться округлением float, что `REQ-RL-002` явно допускает.
Верхняя граница N = 2^53 держит N точно представимым во float.

Семантика квоты — token bucket (всплеск до N, скорость N/W), как задано в intent; строгое «не больше N в любом
скользящем окне W» не требуется (`REQ-RL-001`, находка F-1 первого review).

Отвергнуто:
- Fixed window (счётчик на окно): до 2N запросов на стыке окон, нет непрерывного пополнения `REQ-RL-002`.
- Sliding log (метки всех запросов): даёт строгое «не больше N в окне», но память O(N) на ключ и не token bucket из
  intent.
- Допуск 1e-9 при сравнении с единицей: противоречит правилу «запас меньше единицы — отклонить» (F-1 второго review).
- `fractions.Fraction` для запаса: время источника — float, ошибка уже во входе.
- Фоновый таймер пополнения: требует потоков и реального времени, ломает детерминизм тестов.

### D-2. Внедряемый источник времени

Конструктор принимает `clock: Callable[[], float] | None = None` (секунды); `None` заменяется на `time.monotonic` —
«монотонные часы процесса» из `REQ-RL-001`; невызываемый `clock`, отличный от `None`, — `TypeError` (`callable`); при
создании `clock` не вызывается. В `allow` порядок: `hash(key)` (нехешируемый ключ — `TypeError`, прочие исключения
`__hash__` не перехватываются), затем ровно один вызов `clock()`; исключение часов не перехватывается; значение
проверяется (`int`/`float`, не `bool`, `float(value)` без `OverflowError` и `math.isfinite`, иначе `ValueError`) до
изменения состояния. Время хранится как `float`.

`None` по умолчанию вместо `clock=time.monotonic` в сигнатуре: явный `clock=None` однозначно значит «часы по
умолчанию» (находка F-7 третьего review).

Отвергнуто:
- `time.time()`: не монотонно, не управляется из тестов.
- Передача `now` в каждый вызов: переносит согласованность времени на вызывающего и расширяет API.

### D-3. API

`RateLimiter(limit: int, window: float, clock=None)`; метод `allow(key: Hashable) -> bool` — API зафиксирован в
`REQ-RL-001` (находка F-4 третьего review). Проверки конструктора (`REQ-RL-001`, `SCN-RL-004`): `limit` — `int`, не
`bool`, `1 <= limit <= 2**53`; `window` — `int`/`float`, не `bool`, `float(window)` без `OverflowError`,
`math.isfinite`, `> 0`; иначе `ValueError`. Состояние ключей — `dict` в памяти экземпляра:
равенство ключей — равенство ключей `dict` (тождество или `==` при равном `hash`).

Отвергнуто:
- Исключение при отклонении вместо `bool`: отклонение — штатный исход, а не ошибка.

### D-4. Часы, идущие назад — закрывает `UNK-RL-001`

Решение maintainer'а: при `now < last` — `elapsed = 0` (запас не меняется) и `last = now` (отметка сдвигается назад);
решение по запросу принимается по неизменённому запасу (`REQ-RL-002`, `SCN-RL-005`). Следствие: после возврата часов
вперёд запас пополняется от сдвинутой отметки, то есть отрезок «назад, затем вперёд» засчитывается повторно. Поэтому
гарантия квоты `REQ-RL-001` сужена до неубывающего источника времени (находка F-1 третьего review); для
`time.monotonic` по умолчанию она действует всегда.

Отвергнуто:
- `elapsed = 0` без сдвига `last`: после отката часов пополнение стоит, пока часы не догонят старую отметку.
- `ValueError` из `allow`: для внедрённых часов ошибка перекладывает обработку отката на каждого вызывающего.

> **UNKNOWN** `UNK-RL-001` · blocking — что делает ограничитель, если источник времени вернул значение меньше
> предыдущего (часы пошли назад)? **Решено maintainer'ом:** `elapsed = 0`, отметка сдвигается.

## Risks / Trade-offs

- [Память растёт с числом ключей] → вытеснение вне scope (proposal.md, Non-goals); отмечено в docstring.
- [Ошибка округления float на дробном времени] → допущено `REQ-RL-002`; граничные сценарии на целом времени.
- [Часы «назад, затем вперёд» дают лишнее пополнение] → принято решением по `UNK-RL-001` (D-4).
- [Вызов из нескольких потоков] → вне контракта (`REQ-RL-001`); docstring предупреждает.
