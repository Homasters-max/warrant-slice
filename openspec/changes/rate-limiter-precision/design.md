# Design

## Context

`src/rate_limiter/__init__.py` проверяет окно W и значение источника времени функцией `_finite_seconds`: `int`/`float`,
не `bool`, `float(value)` без `OverflowError` и `math.isfinite`, иначе `ValueError`. Значение `int`, которое double не
представляет точно, она принимает с округлением (2^53 + 1 → 2^53). Решение maintainer'а по `UNK-RL-002` (вариант B) такие
значения запрещает; поведение — `REQ-RL-001`, «значение секунд», сценарий `SCN-RL-007`.

## Goals / Non-Goals

**Goals:**
- Одна проверка «значения секунд» для W и для значения источника времени, как в `REQ-RL-001`.

**Non-Goals:**
- Прочие находки review 4 Change rate-limiter (F-2 — F-8) — см. Non-goals в proposal.md.
- Изменение хранения времени и арифметики пополнения: время по-прежнему хранится как `float`.

## Decisions

### D-1. Проверка точной представимости в `_finite_seconds`

`_finite_seconds(value, what)`: тип `int`/`float`, не `bool`; `seconds = float(value)`, `OverflowError` — `ValueError`;
затем `math.isfinite(seconds) and seconds == value`, иначе `ValueError`. Сравнение `int` с `float` в Python точное, без
приведения `int` к `float`, поэтому `seconds == value` ложно ровно для `int`, которое double не представляет точно
(2^53 + 1), и истинно для 2^53 и 2^53 + 2. Для конечного `float` равенство всегда истинно; NaN и бесконечности отсекает
`math.isfinite`. Функция по-прежнему общая для конструктора (W) и `allow` (значение источника), поэтому правило одно
(`UNK-RL-002`). Порядок проверок `allow` не меняется: ключ, ровно один вызов источника, проверка значения до изменения
состояния.

Отвергнуто:
- Вариант A (`float(x)` конечен, `int` округляется) — решение maintainer'а по `UNK-RL-002` выбрало B.
- Граница |x| ≤ 2^53 для `int`: отклоняет точно представимые 2^53 + 2 и 2^60, а решение требует только точной
  представимости.
- `int(seconds) == value`: то же для `int`, но для `float` лишнее преобразование; `seconds == value` проще.

### D-2. Тесты прежнего прочтения переписываются

`tests/test_rate_limiter.py` закрепляет прочтение с округлением: `test_scn_rl_004_window_in_float_range_accepted`
принимает W = 2^53 + 1, `test_scn_rl_006_clock_value_float_reading` принимает значение источника 2^53 + 1 и 2^53 + 11
(находка F-1 review 1 этого Change). Решение `UNK-RL-002` делает их неверными: W = 2^53 + 1 уходит из параметров
(отклонение проверяет `SCN-RL-007`); тест `SCN-RL-006` проверяет, что 2^53 + 1 от источника — `ValueError` без изменения
состояния, а точно представимые значения за 2^53 (2^53, 2^53 + 12) принимаются и пополняют запас. Проверки переполнения
(`2**1024`) и `sys.float_info.max` остаются: они не зависят от выбора прочтения.

Отвергнуто:
- Удалить эти тесты: проверки переполнения и крайних `float` в них остаются нужными.

### D-3. Подклассы `int` и `float` — вне контракта

Проверка — `isinstance`, поэтому подклассы проходят проверку типа. Подкласс, переопределивший `__float__` или `__eq__`,
может получить от `seconds == value` иной ответ, чем обычное число того же значения; `REQ-RL-001` объявляет такие значения
вне контракта (находка F-2 review 1 этого Change), как и вызовы из нескольких потоков.

Отвергнуто:
- Проверка точного типа (`type(x) in (int, float)`): отклоняет `IntEnum` и прочие честные подклассы, меняя поведение за
  пределами `UNK-RL-002`.

## Risks / Trade-offs

- [Вызывающий, передававший W или часы как большой `int`, получит `ValueError`] → изменение поведения указано в
  proposal.md, Impact; `time.monotonic` возвращает `float` и не затронут.
- [Подкласс `int` или `float` с переопределённым `__float__` или `__eq__` может обойти сравнение] → вне контракта
  (`REQ-RL-001`, D-3).
